## Goal
The candidate keeps a dated list of jobs (and career breaks), schools and projects for their CV, and can put them in the order they want.

## Behavior
Shared by all three pages (`/dashboard/experience`, `/dashboard/education`, `/dashboard/project`):
1. The list loads once per session from `GET api/v1/<collection>/` (cached in the candidate store), sorted by start date, newest first; re-sorted after each save (new, edited or duplicated entry). Empty → empty state with "Add"; load failure → error + retry.
2. "Add" (heading and empty state) opens a modal form. Save: no `_id` → `POST <collection>/create`, else `PUT <collection>/update`. Dates are sent as timestamps (ms); the "current" checkbox is sent as `false` when unchecked; the description is sent as `{ vi, en }`. On success the entry is added/replaced in the list and the modal closes; the API message shows as a toast.
3. Each entry has Edit (modal pre-filled), Duplicate (modal pre-filled, title "Duplicate …", saving creates a NEW entry and leaves the original), and Delete (confirm dialog naming the entry, then `DELETE <collection>/delete/<id>`).
4. Drag-and-drop reorder (a hint "drag to sort" above the list). The order is saved only in this browser: `localStorage['cv-manual-order:<collection>:<candidateId>']`. Entries not in the saved order (new ones) go to the end.

Per section:
5. Experience: "Add" first asks "Experience or career break?". Experience fields: company (required, max 100), position (required), start date (required), end date, "currently working" checkbox, description (Vietnamese required, English optional — `withEnglish`, `src/types/model.type.ts:106`). Career break: break type (required, one of 12 LinkedIn types: career transition, caregiving, full-time parenting, gap year, health, layoff, personal goal, professional development, relocation, retirement, travel, voluntary work), dates, "currently on break", description. Saving a break clears company/position; saving a job clears the break type. A break's title is "Career break — <type>". Experience also has a read-only "View" modal (dates `MM/YYYY - MM/YYYY` or "Present", sanitized description) with an Edit button.
6. Education: school (Vietnamese required, max 255), major (Vietnamese required, 1–255); the English variants are optional but, when filled, follow the same max/min rules, start/end dates, "currently studying", description vi/en (optional).
7. Project: name (required, max 50), position (required, max 100), technology (required; typed comma-separated, stored as a trimmed array, shown joined by ", "), start/end dates, "still working on it", link, description vi/en.
8. *(#400 — spec complete, not yet implemented/sealed)* Experience "View" modal content language: the modal shows a VI | EN toggle (same look and behavior as the VeeForm toggle: radiogroup, `aria-checked`, active option highlighted, aria-label `form.contentLang`). 10. *(#401 — sealed 2026-11-21)* Project type company / personal, linked to an Experience. Backend contract (datvt243/resume-nodejs-api PR #366, released v2.6.0): project has `type: 'company' | 'personal'` (default `personal`; a legacy project without `type` is returned as `personal`) and `experienceId` (string Experience `_id` or `null`, NOT populated — GET returns the bare id). Joi: `type=company` → `experienceId` required, 24-hex; `type=personal` → `experienceId` must be `null` or `''` (backend stores `null`). An id that is not a non-deleted Experience of the same candidate → `400`, `errorCode: 'BAD_REQUEST'`, message `project.experienceNotFound` ("The selected work experience does not exist or has been deleted"), NO `error.details` / no field. Joi failures → `400 VALIDATION_ERROR` with `error.details: [{ field: 'experienceId' | 'type', message }]`.
   - Form: a `type` select (options Company / Personal, i18n keys in `vi` and `en`, default `personal`) and an `experienceId` select. `experienceId` is shown only when `type = company` (model `showIf`, as in `experience.model.ts`) and is then required (yup message `validation.required`). Its options are the candidate's Experience entries excluding career breaks (`isCareerBreak: true`), loaded via `useCandidate({ field: 'experiences' })` and filled at runtime like `PageApplication.vue` `profileId`; option `value` = `_id`, text = `<company> — <position>`.
   - Save: `type` is always sent; `type = personal` → `experienceId: null`; `type = company` → the selected id.
   - Edit / Duplicate of a legacy project (no `type`) → form shows `personal`, Experience field hidden, saves normally as `personal`.
   - Edit of a company project → form shows `company` with its Experience selected.
   - Switching a company project to personal and saving → sends `experienceId: null` (backend unlinks).
   - API errors on save go to the field, not a toast: (a) a `400` with `errorCode: 'BAD_REQUEST'` on saving a project with `type = company` (the backend's field-less "invalid Experience" error) → its message is shown under the Experience select; (b) a `400 VALIDATION_ERROR` whose `error.details[].field` is `experienceId` or `type` → each message under that field. In both cases the form stays open, values kept, NO toast for that error. Every other error keeps today's toast (`handleBase`).
   - Dashboard Project card (`ProjectItem.vue`): a badge "Company" or "Personal" (i18n `vi` + `en`; legacy project without `type` → "Personal"). A company project whose `experienceId` matches an Experience in the store also shows `<company> · <position>` of that Experience (e.g. "Acme Corp · Frontend Developer"). A company project whose linked Experience is not in the store (deleted / missing) keeps the "Company" badge and shows a muted note "Experience removed" (i18n `vi` + `en`) instead.
   - No other display surface changes: CV layouts (`CvResumeLayout.vue`), PagePreview, the public CV, the backend PDF and the JSON Resume export (`toJsonResume`) are untouched.

Dates do not change with the toggle. The footer has an Edit button (`Button action="update"`, text `common.edit`) that closes the View modal and opens the normal Edit form pre-filled with that entry (same as Edit on the card). Viewing sends no API request and changes nothing. Any new label is an i18n key in both `vi` and `en`.

## Edge cases
- Saved order references a deleted entry → that id is skipped.
- Career-break entry edited back into a job → `careerBreakType` sent as `''`.
- `localStorage` unavailable → order works for the session but is not saved.
- (#400) Description is a plain string (legacy) → same text under VI and EN.
- (#400) Description empty in both languages → empty, no error.

- (#402) Legacy project with `technology` empty/missing or `link` empty → that row shows "—", no error.
- (#402) Description is a plain string (legacy) → same text under VI and EN; empty in both → empty, no error.
- (#402) Project with `isWorking` true and `endDate` null → `MM/YYYY - <Present>`.
- (#401) Linked Experience deleted (backend has no cascade) or not in the candidate's list → Edit shows `company` with no Experience selected; saving requires a new choice. Card: Company badge + muted "Experience removed" note (Behavior #10).
- (#401) Candidate has no Experience (or only career breaks, which are excluded) → choosing Company shows an empty select; save is blocked by the required rule. Hint text: not specified (not asked for).
- (#401) Duplicate of a company project → copy keeps `type` and `experienceId`.
- (#444) Legacy school/major/description stored as a plain string → same text under VI and EN; empty in both → "—" for school/major, empty description, no error.
- (#444) `isCurrent` true and `endDate` null → `MM/YYYY - <Present>`.
